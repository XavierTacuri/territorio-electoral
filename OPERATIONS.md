# Operaciones

- Salud: docker compose ps, GET /health, GET /api/v1/health.
- Liveness vs readiness (Fase 4B): `/api/v1/health` (liveness) nunca toca la base de datos — solo confirma que el proceso responde; úselo para el healthcheck del contenedor/orquestador que reinicia un task colgado. `/api/v1/ready` (readiness) sí toca la base y devuelve 503 (nunca 500, nunca detalles de conexión/credenciales en el cuerpo) mientras la DB no esté disponible — úselo como readiness probe del balanceador/ALB para dejar de enviarle tráfico a esa instancia sin reiniciarla. Cuando la base se recupera, `/ready` vuelve a 200 por sí solo, sin reiniciar el proceso API — verificado deteniendo y reiniciando el contenedor de base de datos con las instancias `api` arriba.
- Cada respuesta trae `X-Request-ID` (se conserva el valor entrante si es válido, se reemplaza si es sospechoso o falta) y ese mismo id aparece en la línea de log JSON de esa petición — al investigar un error reportado por un usuario, busque primero por ese id en los logs antes que por hora/endpoint aproximados.
- Los logs JSON redactan automáticamente valores con forma de secreto (tokens Bearer, JWT, credenciales en una URL de base de datos, firmas/credenciales de S3) antes de escribirlos — no dependa de que cada línea de código evite loguear un secreto; la redacción es una capa del logger, no una convención de cada desarrollador.
- Multiinstancia: la aplicación es stateless entre réplicas (ninguna sesión ni reclamo vive en memoria de un proceso — todo pasa por PostgreSQL); dos réplicas pueden recibir tráfico del mismo usuario indistintamente. La única precaución operativa real es no bakear `alembic upgrade head` en el arranque de más de una réplica a la vez (corren en paralelo y compiten por crear `alembic_version`) — ejecute las migraciones como un paso único, antes de escalar a más de una réplica, nunca dentro del `CMD` de cada una.
- Apagado: el proceso API espera a que terminen las peticiones en vuelo y libera el pool de conexiones a la base antes de salir (graceful shutdown) — un `docker compose stop`/`restart` o un despliegue no debería cortar una transacción a mitad de camino; no fuerce `kill -9` salvo que el proceso esté genuinamente colgado.
- `WEB_CONCURRENCY` (workers de uvicorn por contenedor `api`) es una variable de entorno, no un valor fijo de la imagen — ajústela en `.env.production`/`docker-compose.prod.yml` según CPU disponible, nunca editando el `Dockerfile`.
- Frontend: el contenedor `frontend` sirve una build estática de Nginx (no tiene bind mount del código, a diferencia de `api` que sí lo tiene con `--reload`). Tras cambiar código o assets del frontend (por ejemplo `public/map-style.json`) ejecute `docker compose build frontend && docker compose up -d frontend`; un `docker compose restart frontend` por sí solo NO recoge cambios de código, solo reinicia la imagen ya construida.
- Migraciones: docker compose exec api alembic current y alembic check.
- Sesiones: python -m app.scripts.cleanup_auth_sessions --dry-run; quite la opción tras revisar.
- Seeds: solo scripts explícitos; E2E exige APP_ENV=e2e y base separada.
- Informes/alertas/importaciones: use sus comandos en backend/app/scripts; nunca exponga rutas internas.
- Backup: configure DATABASE_URL y ejecute scripts/backup_database.sh DESTINO; archive informes con backup_reports.sh.
- Restore: restore_database.sh ARCHIVO valida; agregue --confirm en ventana de mantenimiento.
- Evidencia y documentos de Jornada Electoral viven en el volumen `evidence_artifacts` (`/app/generated-evidence`) cuando `ARTIFACT_STORAGE_PROVIDER=local`, separado de la base de datos: un backup de solo la DB no los incluye. Respáldelo aparte (`docker run --rm -v evidence_artifacts:/data -v $(pwd):/backup alpine tar czf /backup/evidence_$(date -u +%Y%m%dT%H%M%SZ).tgz -C /data .` o equivalente del orquestador) con la misma cadencia que la base de datos.
- Con `ARTIFACT_STORAGE_PROVIDER=s3` (Fase 4A, AWS): reportes y evidencia/actas viven en el bucket S3 configurado, no en un volumen de este host — el backup de esos artefactos es responsabilidad del propio bucket (versioning + replicación, ver `docs/aws/PRODUCTION_ARCHITECTURE.md`), no de `evidence_$(date).tgz`. La base de datos sigue siendo la única fuente de verdad de qué `storage_key` existe, su tamaño y su sha256 — el bucket nunca sustituye ese rol.
- Simulacro backup/restore verificado (base sintética de desarrollo): `pg_dump --format=custom` → `pg_restore --list` → restaurar en una base descartable (`createdb`/`pg_restore --clean --if-exists`) → comparar conteos de filas (`users`, `campaigns`) entre origen y restaurada → `dropdb`. Con ~1.2 MB de datos el ciclo completo tomó unos segundos; el tiempo en producción escala con el volumen real de datos y debe medirse contra una copia de ese tamaño antes de fijar una ventana de mantenimiento.

Guarde backups fuera del servidor, cifrados, con control de acceso y pruebas periódicas. Retención sugerida: diarios 14 días, semanales 8 semanas y mensuales 12 meses, ajustada a política local. Monitoree espacio de PostgreSQL/informes/evidencia, expiración de TLS, 5xx y latencia. No imprima secretos al diagnosticar.
