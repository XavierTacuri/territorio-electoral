# Territorio Electoral — v3.0.0-rc.1

## Objetivo del RC

Consolidar todo lo construido en el branch `fix/user-creation` (SaaS multi-organización, catálogo territorial de Ecuador, Data Hub de datos oficiales CNE/INEC, Panorama Electoral, Territorio IA, Encuestas, Centro de Comando, PWA de campo offline, Calendario de campaña, Centro de Informes, Alertas inteligentes, Asistente de Debate y Modo Jornada Electoral) en un estado reproducible, sin flakes conocidos y auditado para un primer despliegue en staging. Ningún módulo nuevo se agregó en este ciclo: el trabajo fue exclusivamente estabilización, auditoría de seguridad/RBAC/rendimiento, y documentación.

## Capacidades principales

Ver CHANGELOG.md § 3.0.0-rc.1 para el detalle por área. En resumen: la plataforma cubre desde la administración SaaS de organizaciones/campañas hasta la operación del día de la elección (Jornada Electoral), pasando por inteligencia territorial, encuestas, informes con IA grounded, alertas explicables y un asistente de debate — todo con RBAC multi-rol, aislamiento multi-organización/multi-campaña/multi-cantón, y una PWA offline-first para coordinadores de campo.

## Limitaciones conocidas (por diseño, no por descuido)

- **Nunca es un sistema de resultados electorales.** Modo Jornada Electoral no hace OCR de actas, no compara contra resultados, no cuenta votos. Los resultados oficiales siguen viniendo exclusivamente de CNE.
- Territorio IA nunca predice ganadores, no hace microtargeting, no genera mensajes de persuasión dirigidos.
- Recintos/juntas se pueden crear vía API directa además de importación masiva por Data Hub (decisión de alcance, no un olvido).
- El reemplazo de personal de jornada solo tiene UI para Candidate/Manager; no hay UI de creación de asignaciones nuevas (solo vía API), documentado como alcance deliberado.

## Deuda no bloqueante

- **MEDIUM** — `NeedsPage` lista hasta 100 necesidades sin control de paginación visible (mismo patrón que tenía `AlertsPage` antes de esta corrección, pero sin evidencia de riesgo real hoy).
- **MEDIUM** — Rate limiting de subida de archivos e informes vive en Nginx (local), no en un limitador distribuido; suficiente para un solo nodo, a revisar si se escala horizontalmente.
- **LOW** — `frontend/src/features/operations/CommitmentsPage.tsx` es código legacy sin ninguna ruta ni enlace que lo alcance (0 superficie visible); seguro de eliminar en un ciclo futuro.
- **LOW** — El chunk de MapLibre GL supera 500 kB tras minificar; candidato a code-splitting adicional si el tiempo de carga inicial se vuelve un problema real.

## Instrucciones de staging

Ver `docs/releases/v3.0.0-rc.1.md` (este mismo archivo) § "Staging" en el informe de la fase, y `DEPLOYMENT.md`/`OPERATIONS.md`/`PRODUCTION_CHECKLIST.md` para el detalle operativo. Resumen:

1. Aprovisionar un stack de staging separado de producción: DB propia, volumen de storage propio (`report_artifacts` + `evidence_artifacts`), secretos propios, dominio propio con HTTPS.
2. `docker compose -f docker-compose.prod.yml` (o el manifiesto de staging equivalente) con `backend/.env.production`-style file propio para staging — nunca reutilizar secretos de producción.
3. `alembic upgrade head` contra la DB de staging vacía.
4. Bootstrap del usuario ADMIN inicial (`INITIAL_ADMIN_*` en el env de staging).
5. Sembrar datos sintéticos claramente etiquetados como `[DEMO]` (nunca `seed_e2e`, que es exclusivamente para el pipeline de pruebas automatizadas).
6. Smoke test post-deploy (ver checklist abajo).

## Rollback básico

1. Detener el tráfico nuevo (o mantener el contenedor anterior activo si el orquestador soporta blue/green).
2. Restaurar la imagen previa conocida-buena.
3. Si la migración del RC agregó columnas/tablas nuevas de forma aditiva (como todas las de este ciclo — ningún `DROP` destructivo), la imagen anterior sigue funcionando contra la DB migrada sin downgrade de Alembic. Solo ejecute `alembic downgrade` si una migración específica fue explícitamente destructiva (ninguna lo es en este RC).
4. Si el rollback requiere restaurar datos, use el backup pre-despliegue (ver siguiente sección) — nunca improvise un restore sin haberlo validado antes.

## Backup previo al despliegue

Antes de desplegar el RC en staging (y en cualquier producción futura):

1. `scripts/backup_database.sh DESTINO` (verifica el dump con `pg_restore --list` automáticamente).
2. Backup del volumen `evidence_artifacts` por separado (no lo cubre el backup de la base de datos) — ver OPERATIONS.md.
3. Confirmar ambos backups antes de aplicar `alembic upgrade head`.
